# 腾讯 PanoID 第三轮：地区段、采集段与“车辆编号”假设

调查日期：2026-10-07。所有接口验证为只读请求。已将腾讯旧版城市推荐配置保存为 `tencent-xpconfig-source.js`，它来自：

```text
https://5gimg.map.qq.com/mappc/xpconfig.js
```

## 结论先行

当前证据支持下面的拆分：

```text
前4位 + 第5—8位 + 第9—14位 + 第15位以后
地区/覆盖索引 + 内部采集或场景代码 + YYMMDD + 时间样字段或SCENE字段
```

其中只有前四位和日期前缀有相对稳定的证据。第5—8位不能直接命名为“车辆编号”，也不能直接命名为“地区编号”。它在不同城市、不同景区、不同年份中重复，可能由采集批次、场景来源、设备配置、任务分组等因素共同影响；腾讯没有在公开前端中给出这一段的字段定义。

## 前4位：更像腾讯街景覆盖索引，而非严格行政区代码

腾讯开源覆盖数据项目把 `svid.substring(0, 4)` 称为 `idxId`，并说明它来自手机端 `streetcfg.dat` 的城市／覆盖区域配置。项目 README：

```text
https://github.com/chaofunchengfeng/TencentMapPanoramaCoverageAreaData
```

它还说明：配置中有约281个区域节点，部分旧名称共享同一个 idxId，另有接口迭代后发现但配置中没有的 idxId。因此，前四位更适合叫“腾讯街景覆盖索引”或“区域索引”。

`xpconfig.js` 是推荐城市配置，不是完整 streetcfg。它本轮有149条城市推荐记录、148个不同前缀；其中存在同一前缀重复城市名，例如两个 `2007`：漳州推荐点与龙岩推荐点都使用 `2007`。这证明前缀不能机械等同于当前城市的行政代码。

已确认的典型映射：

| 前缀 | 配置/接口中的地点 | 备注 |
|---|---|---|
| `1001` | 北京 | 天坛、颐和园、八达岭等 |
| `1002` | 上海 | 外滩、陆家嘴、环球金融中心 |
| `1004` | 深圳 | 世界之窗 |
| `1007` | 成都及部分四川样本 | 杜甫草堂、浣花溪；还见普通ID `100710...` |
| `1209` | 忻州/人祖山 | 人祖山场景前缀 |
| `2007` | 龙岩/漳州推荐项 | 云水谣、振福楼等 |
| `2107` | 赣州 | 宋代古城墙 |
| `2820` | 凉山 | 螺髻山 |
| `3208` | 平凉 | 崆峒山 |
| `3403` | 吴忠 | 黄河楼 |
| `3514` | 阿勒泰地区 | 五彩滩 |

`ad_code` 也不能替代前四位。很多景区 ID 的 `ad_code` 为空，已经返回的非空值是六位行政区代码，例如环球金融中心为 `310115`、颐和园为 `110108`。因此建议同时记录 `region_prefix`、`ad_code`、`addr`，不要互相替代。

## 第5—8位：已证实是内部代码段，但“车辆编号”仍未证实

### 直接复用样本

从腾讯旧版 `xpconfig.js` 与 `/sv` 元数据中，确认以下重复：

| 第5—8位 | 地点 | 前缀/日期示例 |
|---|---|---|
| `10YF` | 平凉、吴忠、渭南 | `3208`、`3403`、`3104` |
| `30U1` | 咸宁、怀化、鄂州、黄冈、晋中 | `2410`、`2512`、`2405`、`2409`、`1207` |
| `30X4` | 沧州、衡水、淮安、盐城、商丘、宜昌、阿坝 | 多个区域 |
| `30U8` | 黄山、宣城、马鞍山、芜湖 | 多个安徽城市 |
| `30W6` | 南通、成都景区内部 | `1704` 与 `1007` |
| `70W6` | 连云港 | 与 `30W6` 同尾码、不同前缀 |
| `30V7` | 凉山 | 推荐配置与螺髻山场景 |
| `70V7` | 赣州 | 宋代古城墙 |
| `10YF` | 华山、崆峒山等场景 | 景区与城市均出现 |

这说明第5—8位不是区域前缀。它仍然可能是车辆或车辆组编号，因为同一采集车可以跨城工作；所以“跨城复用”本身不能排除车辆含义。但目前没有字段、注释或一辆车的连续行程证据能证明它就是车辆号。

同一景区内部也出现代码变化，尤其是室内或大型景区：

```text
1004 + 15-01 / 36J7 / 34J7 / 39J7 ... 世界之窗
1002 + 35J3 / 36J3 / 37J3 ... 上海俏江南不同区域
1007 + 30W6、31W6、32W6、33W6、34W6、35W6、36W6 ... 成都浣花溪及四川博物院关联区域
```

更准确的当前命名是：

> 第5—8位为腾讯内部采集／来源／场景分类段；其中部分代码可能与车辆或设备组相关，但“车辆编号”尚未被公开证据证明。

### `vehiclesRestricts` 不是街景车辆编号表

旧版腾讯前端 `Main.js` 确实包含名为 `vehiclesRestricts` 的对象，但其实际调用是计算每周一到周五的城市车牌限行尾号，并生成“限行尾号”提示：

```javascript
vehiclesRestricts = [
  { begin: "20160110", rules: [{number:[3,8]}, ...] },
  ...
]
```

紧随其后的函数根据当前日期生成“周一／周二”等限行信息。这个对象与 PanoID 没有读取关系，不能用来解释第5—8位，也不能据此推导采集车编号。

## 第9—14位：前端只把它作为年月日的一部分

腾讯旧版前端明确使用：

```javascript
c.slice(8, 10)  // YY
c.slice(10, 12) // MM
```

开源构建脚本则把 `slice(8,10)`、`slice(10,12)`、`slice(12,14)`、`slice(14,16)`、`slice(16,18)`、`slice(18,20)` 组合成日期时间，用于按时间分线。

因此对普通道路 ID，`第9—14位 = YYMMDD` 是很好的工作假设。例如：

```text
10071018150810111249700
前4位 1007 | 段1018 | 150810 | 11:12:49.700
```

但它不是完整 ID 的通用语法。早期景区/室内样本中，第15位以后可能不是合法的 `HHMMSSmmm`：

```text
10041501111222150789000
尾段按时间切分得到 15:07:89.000，秒数无效，但 ID 有效
10041501111222144483000
尾段得到 14:44:83.000，ID 有效
```

因此这些尾字段更可能是“时间样字段＋序列/编码”，或不同来源使用了不同编码，不应强行当作真实时分秒。

## `SCENE` 型是另一种尾段语法

例如：

```text
121030J31501070SCENE006
20033XTY1402050SCENE009
350630W01406200SCENE004
```

在这些有效样本中，日期样字段仍在中间，但末尾使用 `SCENE###`。其中：

- `121030J31501070SCENE001—008`：人祖山 8 个有效场景。
- `351431W01406200SCENE001—007`：五彩滩 7 个有效场景，008/009 未命中。
- `200730U314041911...`：龙岩云水谣使用普通数字尾字段，内部仍有 `linkpois` 关联。

SCENE 序号是场景编号，不应理解为车辆编号。`all_scenes` 为空时也不能据此认为不存在后续 SCENE；五彩滩就是反例。

## 当前最可信的 ID 解析器规则

不要把所有 ID 解析成同一种格式。建议按下面顺序：

1. 先查询 `/sv`，以返回的 `basic.svid` 判断 ID 是否有效。
2. 若 ID 包含 `SCENE`，用 `SCENE###` 作为场景编号，前面的数字部分只按样本记录，不强行解析为时间。
3. 对普通数字尾 ID，先切 `region_prefix=id[0:4]`、`segment=id[4:8]`、`date_field=id[8:14]`。
4. `date_field` 用 YYMMDD 验证；如果月份或日期非法，保留原文并标为非标准批次。
5. 尾段只有在 `HH<24、MM<60、SS<60` 且 ID 属于普通道路类型时，才按 `HHMMSSmmm` 候选解析。
6. 以 `basic.type`、`basic.mode`、`basic.source`、`basic.scenic_id`、`basic.rdid`、`region.entrances`、`linkpois` 和 `history.nodes` 作为实际语义字段。
7. 不要把 `rdid`、`scenic_id` 或 `vehiclesRestricts` 反推为车辆编号。

本轮没有找到腾讯官方对第5—8位的字段注释，因此“车辆编号”仍是候选解释，不是结论。
